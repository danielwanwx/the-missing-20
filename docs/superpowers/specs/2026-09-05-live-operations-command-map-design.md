# Live Operations Command Map Design

Date: 2026-09-05
Status: selected visual direction, pending implementation
Selected direction: Flow-First Command Map (visual option 2)
Visual target: `docs/design/references/live-operations-command-map-option-2.png`

## Product outcome

The recording must show an operational system changing over time, not a completed incident report. A judge should be able to watch a 100-unit receipt become an 80-unit ERP record, see a 20-unit gap emerge, watch the agent correlate evidence across isolated SaaS systems, and see the manager-approved recovery return the authoritative state to 100.

The frontend remains a human-controlled agent platform. Monitoring and read-only diagnosis can advance automatically. A human must deliberately open the investigation and approve the bounded write. Verification remains an independent authoritative reread.

## Information architecture

The primary navigation has two destinations:

1. **Dashboard** — live operational truth, time-series change, cross-system flow, and the current agent lifecycle.
2. **Investigation** — agent reasoning, evidence, tools, hypotheses, chat, manager review, bounded execution, and verification.

`Scenario Lab` leaves primary navigation. Its controls move into a small `Demo Controls` drawer available to the presenter. This drawer can select Normal, Inject incident, and Recovery, but it must never look like an end-user workflow.

The Dashboard does not contain the full Agent topology. It exposes one compact Agent status bar and one `Open Investigation` action. The Investigation page is the only place that visualizes the Agent reasoning graph.

## Dashboard composition

### Header

- Brand: `THE MISSING 20`.
- Primary destinations: `Dashboard`, `Investigation`.
- Right side: connection state, authoritative sequence, and `Demo Controls`.
- The incident mode is visible but does not displace the live content.

### Live Operations Command Map

The top-left hero shows the deterministic business chain:

`Warehouse → Message Queue → ERPNext → Invoice → Recovery`

Supporting systems appear below the stage they inform:

- Airtable Quality → ERPNext eligibility evidence.
- Celigo → receipt transport and acknowledgement.
- Jira → incident correlation.
- Slack → manager approval evidence.

Every node displays one current authoritative value and one concise state. Connectors are thin, solid, and anchored exactly to node boundaries. Aligned relations use straight paths; offset evidence relations use restrained curves or rounded orthogonal routes. Paths must not enter unrelated nodes, stop short, cross without meaning, or use glowing endpoint dots.

The active event is represented by a small moving packet or current-position marker driven by the newest server event. It is not a decorative loop: when no event arrives, the marker does not move.

### Performance Over Time

A synchronized chart shows three server-derived series on one shared time axis:

- Expected: 100 units.
- Recorded: 100 → 80 → 100.
- Gap: 0 → 20 → 0.

The chart includes the anomaly, diagnosis, approval, execution, and verification moments. A vertical `NOW` cursor tracks the latest authoritative sample. New samples append from the right. Historical samples remain stable and are never regenerated by a client timer.

The chart replaces the hidden legacy incident chart. Incident mode must not hide it.

### Event Rail

The right rail behaves like a live market tape:

- Oldest visible event at the top, newest event entering at the bottom.
- New rows slide upward into place and receive a brief source-colored highlight.
- Auto-scroll follows the newest row unless the user has intentionally scrolled away.
- A pinned `NOW` edge and connection indicator distinguish live, reconnecting, paused, and replay states.
- Each row shows timestamp, source, action, state, and an evidence affordance.
- Provenance is summarized once at rail level. Repeating `DEMO` on every row is removed.

The event rail groups rows by operational phase when enough events exist: Correlating, Diagnosing, Manager Review, Recovery, and Verified.

### Agent status bar

The bottom strip shows:

- Current lifecycle stage.
- Evidence count.
- Confidence when supplied by the agent result.
- Required next human action.
- `Open Investigation`.

It is a status and navigation surface, not a duplicate topology.

## Investigation Workspace

The Investigation page owns the agentic workflow:

- Multi-SaaS evidence topology centered on the Agent.
- Streaming tool calls and evidence returns.
- Hypothesis creation, support, elimination, and unresolved states.
- State-aware chat grounded in the current evidence ledger.
- Manager review only when a bounded write is ready.
- Execute recovery and verify receipt as separate actions.
- Resolution packet with evidence, approval, idempotency, timestamps, and authoritative reread.

The old supply-chain diagram is removed from this page because the Dashboard owns business-system flow. The left rail becomes a compact evidence-source/status rail. The central surface focuses on agent reasoning. The right rail retains Context, Chat, and Decision, but inherits the same light theme as the Dashboard.

No Dashboard focus overlay or theme state may leak into the Investigation view. View-specific classes and selectors must be scoped to the active panel.

## Contrast and visual system

- Typeface: local Geist and Geist Mono.
- Page: light silver `#e8ecef`.
- Primary surfaces: white `#ffffff`.
- Primary text: charcoal near `#17212b`.
- Secondary text: no lighter than a readable slate near `#52616d` on white.
- Muted metadata: no lighter than `#667580` unless it is decorative and hidden from accessibility APIs.
- Status colors remain pure solid accents: blue, cyan, green, orange, violet, and coral.
- No gradients, double-tone topology nodes, broad dark overlays, or low-opacity text.
- Body and event-row copy targets 14–16 px at the desktop recording viewport.
- Color never carries state alone; every state has a text label or icon.

## Data and event flow

1. The backend publishes the authoritative snapshot and ordered event ledger.
2. The Dashboard projects the snapshot into node values and appends telemetry samples to the chart.
3. Each ordered SSE event advances the active packet, appends one event-rail row, and briefly highlights the affected source and chart marker.
4. Automatic diagnosis reads scoped evidence and publishes tool/evidence events without granting write authority.
5. `Open Investigation` deep-links into the same incident and sequence without starting a second run.
6. Manager approval binds the exact proposed quantities.
7. Execution applies the bounded idempotent recovery.
8. Independent reread appends the verified sample and closes the gap.

Dashboard, Investigation, and Demo Controls must consume the same incident identifier, sequence cursor, snapshot, and event ledger. They may not maintain independent mock timelines.

## Motion behavior

- Event activity is event-driven, not timer-driven.
- New event rows enter from the bottom and shift earlier rows upward over 220–320 ms.
- The corresponding source node and chart marker receive one short state pulse.
- The active packet moves only when a new event establishes a new source-to-target relationship.
- `prefers-reduced-motion` replaces translation with an immediate state/color change.
- Stream loss freezes motion, labels the surface `RECONNECTING`, and preserves the last authoritative sample.

## Error and empty states

- No snapshot: show a compact `Waiting for authoritative stream` state without drawing invented data.
- Insufficient history: render values and a two-point baseline rather than an empty oversized chart.
- Stream disconnected: freeze `NOW`, preserve data, and expose reconnect status.
- Agent unavailable: Dashboard monitoring remains functional; Investigation explains that deterministic evidence and policy remain available.
- Missing optional SaaS source: show the source as unavailable and exclude it from evidence counts.
- Closed incident: retain its historical curve and events while clearly labeling replay/history mode.

## Accessibility and interaction

- All graph nodes are buttons or accessible links with system, value, and state names.
- Chart has a textual summary and keyboard-focusable samples.
- Event rail uses ordered semantics and announces only the newest event, not the entire rebuilt list.
- Auto-scroll pauses when the user scrolls or focuses an earlier event.
- Primary actions meet minimum target size and show visible focus.
- No essential label relies on low-contrast monospaced styling.

## Implementation boundaries

- Reuse the existing API, SSE stream, telemetry history, reconciliation-series helpers, canvas chart utilities, source adapters, and bounded execution endpoints.
- Replace the incident-mode `legacyDashboard.hidden = enabled` split with a single live Dashboard composition.
- Do not duplicate the event ledger, generate client-side samples, or introduce a second scenario state machine.
- Extract Dashboard, Investigation, event-rail, and topology rendering into bounded functions before adding new presentation behavior; avoid expanding one monolithic render path further.

## Verification

### Automated

- Dashboard retains the time-series chart during an active incident.
- Recorded and Gap series append from authoritative snapshots and close at 100/0 after verification.
- Event order is ascending visually and newest events enter at the bottom.
- No event-driven animation runs without a new sequence.
- Dashboard contains no full Agent topology.
- Investigation contains no duplicated deterministic supply-chain map.
- Scenario Lab is absent from primary navigation and remains reachable through Demo Controls.
- Every connector terminates on its source and target boundary.
- Contrast tokens and minimum font sizes are regression-tested.
- Existing diagnosis, chat, manager approval, execution, verification, replay, degraded, and fail-closed tests remain green.

### Browser QA

- Capture Normal, Incident forming, Investigation running, Manager review, and Verified states at 1440 × 1024.
- Confirm chart, topology, event rail, and Agent status advance together from the same sequence.
- Verify event auto-scroll, manual-scroll pause, keyboard focus, reduced motion, reconnect, and narrow-screen stacking.
- Compare the implementation against the selected visual target in one combined image.
- Require zero console errors and a `design-qa.md` result of `passed` before handoff.

## Acceptance criteria

At the recording viewport, a first-time judge can answer these questions without opening a debug surface:

1. What changed, and when?
2. Which business system disagrees with the others?
3. What evidence is the Agent reading now?
4. What conclusion did the Agent reach?
5. Why did the workflow stop for a human?
6. What exact bounded action was approved?
7. Did the authoritative state actually recover?

The frontend is complete only when the answers visibly emerge through the same end-to-end run rather than appearing all at once as a completed report.
