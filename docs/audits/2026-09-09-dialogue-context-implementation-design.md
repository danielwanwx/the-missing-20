# Recoverable dialogue context: implementation design

Status: DESIGNED, NOT_IMPLEMENTED. Independent backend review supports this bounded design. It does not claim multi-user authentication, semantic validation of old answers, or an implemented Strands session.

The gateway starts a new Agent per HTTP request and retains three prior display turns. Failed model prose must never enter recoverable context. A runtime-valid answer can still be semantically wrong, so restoring prior explanations as facts is unsafe. Existing application dialogue_intent remains the authority for refusal on every request.

Scope the first implementation to the existing single-operator local demo using a persisted runtime_instance_id, case_id and stable conversation_id. No per-question run UUID as session identity. A case change or explicit new conversation changes scope. Preserve at most twelve user requests within the existing question length limit, with request IDs and times; these are untrusted requests, not resolved facts or preferences. Save requests before inference. Persist only runtime_validated record-reference candidates after successful validation; rejoin them against fresh sources every turn. Retain changed/ambiguous status when candidates disappear. Never persist executable plans, approvals, source quantities, policy labels, assistant explanations or failed candidates into this context.

Native SnapshotSessionManager is a storage candidate, not a reason to replay the inference Agent's history. Installed 1.53 supports manual snapshots with save_latest_on='trigger'. A no-inference context carrier may save only whitelisted state; restore and validate it before constructing the new inference Agent. This must perform zero model calls and zero business writes. Use existing storage where a second store creates avoidable inconsistency; demonstrate a concrete native integration benefit before adopting it.

Serialize same-scope requests or use revisions to prevent lost updates. Validate schema and runtime/case/conversation identity before restoration. A failed restore must be visible and must not revive old plans. Legacy display history is not automatically migrated into proven memory; only user text and revalidated references qualify. This step does not enable summarization or upgrade the SDK.

Acceptance: sixth-turn reference and refusal; restart; failed invocation and internal rejected candidates excluded; correction treated as a claim; changed/deleted reference; cross-case/runtime isolation; concurrent save; corrupt/old schema and interrupted save; twelve-request bound with refusal retained outside truncation. After offline review, run frozen D4/D5 and relevant held-out sequences with current sources, model and budgets. Report all failures and costs. Summary is a separate S1 comparison, not a prerequisite for continuity when explicit bounded context works.

## Independent review of the reduced S2 implementation

Verdict: **APPROVED TO IMPLEMENT**, subject to the interfaces and acceptance boundaries below. This amendment supersedes the Snapshot carrier proposal for this slice. Reuse the existing persisted `dialogue_intent` in both platform implementations; do not add a second store, native session carrier or model-generated summary. No native session integration is claimed. The supported identity boundary is one operator in one local runtime with one server, not authenticated multi-user isolation or cross-process coordination.

Add a versioned schema and stable `conversation_id` to `dialogue_intent`; keep it stable across same-case requests and process restoration, and regenerate it on case change or explicit new conversation. Continue storing at most twelve original user requests with request identity/time. Migrate legacy state conservatively without treating display answers as validated memory. Application refusal/authority remains a separate persisted source of truth and must survive context omission. Invalid schema/scope must not revive old conversation state or erase the application's refusal state.

The gateway must acquire its instance serialization lock **before** calling `platform.current()`, then build and save context from that fresh projection. Hold serialization across the same-scope read/update/inference/result sequence so a second request cannot overwrite state derived from a stale projection. Persist the new user request before inference; preserve it on provider, budget and validation failure. Do not retain rejected candidates or assistant explanations from either the real-source or synthetic branch. Current ERP is reread on every invocation; source unavailability keeps the existing safe-stop boundary.

Construct model input from whole user messages within the existing 4000-character question limit; do not enlarge the limit or silently cut a sentence. Reserve the complete current question first, including wrapper and required current authority/context overhead when calculating available history space. If the current request alone cannot fit the endpoint's accepted bound, return an explicit input/context limit outcome rather than truncate it or invoke on altered text. Pack earlier whole requests in recency priority and present retained requests chronologically. Report actual omitted-request counts, including omission caused by the twelve-request retention bound where that count is tracked; do not claim the model saw every stored request. Persisted storage capacity does not imply all twelve requests fit one model input.

Reference state is a candidate group, not an accumulated union: persist admitted receipt IDs plus their associated user question for each successful runtime-validated reference-bearing turn. Select the most recent such group across intervening turns without references. Do not drop the group merely because the immediately previous answer cited none; do not merge unrelated groups or silently choose a first pair. Rejoin the selected group against this turn's current authoritative receipt set, preserving missing and ambiguous status instead of silently treating surviving IDs as a complete original group. Explicit current-question objects take precedence over historical candidates. `runtime_validated` describes provenance only, not semantic correctness of the old answer. Store no quantities, executable plans, approvals, expected dispositions or assistant claims in this structure.

Required offline checks before live D4/D5:

- Sixth-turn and restart continuity in both persistence implementations, preserving original user wording, stable same-case conversation identity and application refusal.
- Provider/validation failure preserves the failed request but no assistant candidate; synthetic and real-source branches both restore user-only context.
- Concurrent asks start from fresh state inside the lock and retain both requests without duplicate or lost updates.
- Boundary-sized current question remains whole; long historical messages are omitted whole; actual model input remains at most 4000 characters, omission counts are truthful, and refusal is independent of truncation.
- An early valid receipt group survives no-reference turns; a later valid group replaces rather than unions it; explicit new objects win; deleted/changed, wrong-case and ambiguous references remain visible as unresolved.
- Case change, old/corrupt schema and explicit new conversation do not leak prior context. Repeated current-source reads and source-unavailable failure remain intact. Restoration performs zero model calls and zero business effects.

After code freeze, independently review the implementation and run the frozen relevant D4/D5 sequences with unchanged source/model budgets, recording failures, costs and latency. This slice can establish bounded cross-HTTP user-intent continuity; factual accuracy, complex reasoning, safe execution and native S1 compression remain separate acceptance dimensions.
