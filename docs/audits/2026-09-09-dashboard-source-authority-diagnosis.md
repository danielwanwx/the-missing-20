# Dashboard source-authority smoke diagnosis

Date: 2026-09-09. Independent backend/product consistency diagnosis. Read code, current CSS/HTML, domain tests and the older staged-flow design; did not modify implementation, execute a browser session or independently reproduce pixels. The reported smoke observation is supplied by the parent: incident `M20-PO-4817`, receipt posted 88, queue 12, legacy failed cells 20. Current base HEAD during inspection: `f943872`; pending UI edits existed and were not reverted.

## Finding

**P1: the smoke asserts an obsolete combined surface contract, and the UI still maintains an unrelated legacy detail projection behind a newer case projection.** Changing the expected 80 to 88 alone does not verify coherent authority. Equally, reverting the dashboard to legacy 80/20 would break alignment with the current Case Console's two-cause case.

Critical numeric distinction: the primary Case Console is **100 physically arrived, 80 available, 8 quality-held, 12 receipt-unresolved** (`domain/ambiguous_receipt.py::primary_case`, checked by `test_ambiguous_receipt_case.py`). The current frontend derives **88 receipt-posted = 80 available + 8 held**, while the unresolved-receipt queue is 12. The overall availability gap is **20 = 8 + 12**. Thus 88/12 can be correct for *posted/receipt-unresolved*, while 80/20 can be correct for *available/total-unavailable*. They are not interchangeable quantities. Legacy 20 `QUEUE_FAILED` unit records specifically describe an entirely queued 20-unit failure, not the new 12-plus-8 decomposition.

## Contract and actual rendering path

The September 5 staged-flow design explicitly specified a synthetic session ledger whose Warehouse/Queue reaches 100 while ERP/Invoice stops at 80 with 20 queued. `scripts/run_decision_workspace_smoke.py` around line 1160 still expects that legacy incident URL and 80/20 flow totals plus 20 failed density cells after the server scenario transition.

The newer code's explicit authority contract differs: `platformFlowProjection()` chooses `live-read` always, or `synthetic-demo-fixture` for a non-normal selected scenario. Its comment requires one Case Console authority in both views and keeps the separate normal baseline isolated. `selectScenario()` still transitions the legacy session through `/api/v1/scenarios` and then synchronizes the platform investigation. `renderFlow()` selects the platform counts and changes the recorded label to `RECEIPT POSTED`. The case ID in the supplied failure also reflects the platform case. This is therefore not evidence that the server failed to create an incident.

`renderUnitDensity()`, `renderUnitAnomalies()` and unit detail still use `state.snapshot`/`state.units`, i.e. the separate legacy per-unit ledger. But **the current CSS already hides these controls whenever `body[data-agent-platform="ready"]`**: density strip, selection detail and inspector are `display:none`. `renderAgentPlatform()` sets that attribute whenever a platform exists. Hence the smoke's query counts legacy DOM nodes regardless of their visibility. The supplied failure does not by itself establish a visible 20-cell contradiction. Do not report unseen DOM as screenshot-confirmed visible content.

The hidden stale content remains a fragile implementation boundary, and the smoke does not enforce the intended visible authority. The flow's literal `gap` label is also potentially misleading: `#queue-count` displays `receiptUnresolved` (12), while the platform's total gap includes quality hold (20). It must be labelled as receipt-unresolved/queue gap or displayed alongside the separate quality-held quantity. This is a real user-facing semantic distinction, not an optional numeric rounding fix.

A further audit target is the event rail: `dashboardEvents()` uses only platform events for live authority, but merges legacy ledger events, platform events and provider reads for the synthetic selected case. `chartTelemetryPoints()` already prefers platform events when `platformFlowProjection()` exists. The rail must not narrate legacy 20 queued as the same case fact as platform 12 unresolved + 8 held. This is a code-level mixing risk; this review did not prove which rows survive its final filters in the current browser.

## Minimal safe repair direction

1. Preserve the current selected-case platform authority for dashboard header, flow, charts, investigation, recovery and source-linked details. Keep the normal synthetic session separate and preserve its server transition controls; do not delete the scenario or live modes to make smoke pass.
2. In platform authority mode, clear and explicitly hide legacy unit density/anomaly/detail DOM and cancel stale unit selection. Do not synthesize 100 per-unit identities from aggregate Case Console quantities. Restore legacy rendering only for the actual legacy/normal surface if required, retaining its real unit-detail functionality there.
3. Express quantities accurately: arrived 100, receipt posted 88, available 80, quality held 8 and receipt unresolved 12, with total unavailable 20 only where that metric is intended. Do not rename all 12 as quality-held or all 20 as queue failed. Keep meaningful flow nodes, metrics and evidence access; a minimal label correction is preferable to a new visualization system.
4. Audit each visible dependent surface (header, KPI, flow, chart, event rail, inspector, case links) against the selected case ID/provenance. Platform mode should not fall back to legacy business facts when a platform field is unavailable. Normal mode can retain its own ledger. Control-plane transition messages may coexist only as clearly separate operational events, not warehouse facts.
5. Then update the smoke to check the selected server/platform case and **semantic values against its actual API projection**, including available vs posted and quality vs receipt gap. Verify the legacy density/detail is absent or hidden/empty and not the selected case's evidence. Do not replace literal 80 with 88 while retaining the legacy 20-cell assertion or arbitrary URL-based equivalence.

### Phase C — non-negotiable negative controls and evidence

Preserve current HTTP response/error checks and immutable replay checks. Add or retain at the appropriate API scope: unknown case; wrong/missing role; stale plan/version; execute before approval; repeated identical command; browser refresh and reconnect; source-unavailable state; refusal that produces no effect; old-case action after switching cases. Compare exact business-effect IDs and counts, not only success text. A real mouse/key path must still demonstrate the current visible controls through at least one complete authorized local workflow; API calls alone do not replace UI reachability.

**Do not claim server-restart coverage currently exists in this script.** The inspected code closes/reopens browser pages but does not reconstruct `DecisionWorkspaceServer` over the same runtime after shutdown. Browser reload is not process restart. Preserve any separately established restart tests, and add an explicit server stop/recreate/current-read step if this smoke's release contract is to claim restart durability. Repeat commands after restart against the same persisted intention and verify unchanged effect identities. This can be a final bounded block; it must not invoke real providers.

Similarly, a command carrying an `idempotency_key` is not proof of replay safety until the same command is actually repeated and before/after effects compared. Existing immutable replay checks remain valuable but read replay alone does not prove command idempotency. The current script's manifest must not overstate either property.

### Phase D — rollout and stop conditions

Implement product authority/labels first, freeze the visible contract, then replace tests in the above order. Run each bounded block while preserving the original full-smoke failure until the entire revised script passes. Independent review must inspect changes to expectations together with the product change and raw API traces. Keep failed attempts as evidence; do not remove failing branches, shorten the test after the last passing screenshot, or label partial browser success full smoke.

A reasonable small implementation is shared helpers to capture current API authority, assert actual element visibility, and compare selected-case quantities; avoid a new browser framework. The legacy API block can reuse existing helpers unchanged. Stop and diagnose any newly discovered authority mismatch before adjusting more expectations. The final deliverable remains a complete passing smoke with an accurate scope manifest plus independent review, not this checklist or a collection of partially passing replacements.
