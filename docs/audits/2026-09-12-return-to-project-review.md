# LogisticPilot / The Missing 20：当前审查、前景与更新优先级

审查日期：2026-09-12，Pacific。范围：真实运行状态、核心代码与测试、产品任务、竞品与商业验证、截止日前更新顺序。**本轮交付是审查和可执行的优化清单，没有修改产品代码或重新执行业务写入。**

## 结论

**继续 The Missing 20，但先修复当前可用性和证据语义，再验证 Agent 的额外价值。不要扩大成通用 WMS/TMS，也不要再进行整站视觉重做。**

工程基础和限定业务链值得继续：本轮直接读取配置的真实 ERP，仍得到 PO20 收货 40、发运 40、客户 A/B 发运 25/15。原生单据与限定规则已经提供了可以检查的工作结果。与此同时，当前网页的真实 Ask 返回 500，后台说明当前 AWS 角色不具备所选 Opus 模型的 InvokeModel 权限；留存证据到模型的传递还存在事实新鲜度错误。这些优先级高于更多模型、更多 Agent 或更多系统标识。

市场结论是**适合用一个窄场景寻找设计伙伴，尚未证明产品市场匹配**。合适切口是 ERPNext 零部件分销团队的收货/质检异常与客户履约协同。已有 ERP 原生能力、D365、SAP 和 Odoo 都是实质替代；连接器数量不能成为核心差异。详见 [市场复核](../research/2026-09-12-logisticpilot-market-review.md)。

### 测试结果

`make check` 的格式检查通过（270 个文件），Ruff 通过，配置的 mypy 核心检查通过（51 个文件）。第一次 Python 全量执行得到 **1,937 passed / 19 skipped / 2 failed / 48 errors**，失败和错误均指向沙箱不能绑定本地测试端口。

针对这些失败项在允许本地端口的环境下执行 `python -m pytest --lf -rA`，结果 **50 passed / 44 deselected**。另行执行 `npm test`，**141 passed / 0 failed**，其中 distributor 前端模块单独 40 项通过。前面的六个核心 Python 模块定向检查也通过。

准确表述是：**首次全量检查的 50 项环境阻塞已在定向重试中通过，其余 19 项仍跳过；没有单次全量 `make check` 绿灯，也没有成功的本轮真实 Agent 对话。** 通过离线测试不覆盖下述新发现的语义缺口。

## 2. 优先修复的缺陷

优先级 P0 指当前核心入口不可用；P1 指证据语义会影响判断；P2 指应在本轮集中修正的错误恢复/信息暴露问题。下面列的是已证实的问题，非假想的生产风险清单。

### R01 / P0：当前真实 Agent 不可用

**复现**：打开 Agent board，询问 PO20 数量、资料时间及物理交付边界；界面显示 `Request failed (500)`。第二次直接只读请求收到 Bedrock `AccessDeniedException`。当前角色缺少所选 Opus 4.6 inference profile 的 `bedrock:InvokeModel` 权限。公开报告不保留完整账户 ARN。

**修复方向**：先确定已授权、预期使用的模型和运行身份，修正身份/配置错配并在同一应用路径验证。若必须新增 IAM 权限，应单独处理明确的权限边界；不能用反复 `aws login` 替代权限诊断，也不能静默降级模型。

**验收**：相同网页成功完成 3 个短的真实回合：数量与客户、短缺和样本质检因果、物理交付/财务证据边界；记录实际模型、来源模式与日期。一次来源不可用场景不能返回成功结论。无需为这项验证执行新订单或写入 ERP。

### R02 / P1：留存证据被模型输入重新标为 CURRENT

**代码依据**：[packet 构造](../../scripts/decision_workspace_server.py) 的 `_distributor_native_packet`（基线第 1080 行）硬编码 `status: CURRENT`，未保留 projection 的 `evidence_mode`、`live_source`、`as_of`。留存数据因 `available=True` 可进入 Ask；[原生对话包装](../../src/the_missing_20/adapters/native_receiving_dialogue.py) 第 200–205 行又将其称为当前来源。

**独立复现**：输入具有 `RETAINED_AS_OF` 的合成 projection 后，输出工具 payload 丢失上述日期/模式，并出现 CURRENT。**错误输入已证明；本轮没有观察到模型据此给出的错误答案，因为真实调用先被权限阻止。**

**修复方向**：把同一组来源模式与有效时间贯穿 projection、工具 payload、SDK 当前回合上下文和最终显示。CURRENT 表示本回合实际新读取；RETAINED 表示指定时间留存。资料缺失不补造日期或实时性。

**验收**：分别用 fresh、retained、unavailable 输入检查结构，并以相同问题做真实 fresh/retained 两次比较。模型应说明来源边界，不能只靠 UI 在答案外加一个留存 badge。

### R03 / P2：已完成事件的确认响应会倒退到旧数量，并标最新时间

**代码依据**：[distributor_operations.py](../../src/the_missing_20/adapters/distributor_operations.py) 第 591–596 行读取原事件的历史 `result_json`，第 625–626 行却为它附上最新留存时间。已有 `stored_result` 分支也使用相同标记模式。

**独立离线复现**：合成 R4 数据先收到 20 Box，再收到 19 Box。当前 projection 为 39；确认引用第一个事件的完成记录，响应退回 20；下一次 projection 又为 39。旧的 20 被标成与最新 39 相同的 `as_of`。没有 ERP 调用。这是多事件恢复条件的缺陷，**不是声称 PO20 当前的 40 已被改坏**。

**修复方向**：返回最新案例状态，并单独附上该历史事件的确认信息。历史事件结果保持自己的日期，不能伪装成最新全案状态。

**验收**：两个以上事件之后确认较早事件，当前总量不回退；历史日期正确；重复确认不产生 ERP 或 SaaS 效果。现有留存测试只有一个事件，需补这项真实状态差异的回归。

### R04 / P2：模型提供方错误穿透到通用 500

**代码依据**：`_distributor_native_ask_turn` 第 1296–1301 行的捕获列表不包括 `botocore.exceptions.ClientError`；通用 HTTP 异常边界第 2597–2599 行返回 `str(exc)`。本轮实际 API 暴露了提供方 ARN/权限细节，前端反而只显示笼统 500。独立合成 AccessDenied 复现也证实异常原样穿透。

**修复方向**：在模型边界转换成现有、可操作的 UNAVAILABLE 结果；客户端展示“模型访问被拒绝/需要检查配置”，内部诊断保留关联标识和分类，避免向客户端返回原始提供方细节。不能吞错后显示假答案。

**验收**：权限拒绝、凭据失效和服务超时均得到不同且安全的分类；输入保留，可重试；不改变真实业务状态。

## 3. 产品与可复现性缺口

### R05：新进入者的启动路径与当前产品不一致

README 的 Quick start 引导 `make case-console` 与旧的 Live / Inject incident；当前主流程却是需要额外配置的 `/operations`。`.env.example` 没有当前 distributor 模型、原生对话、case 配置与留存模式的完整入口。当前可见运行还依赖私有配置文件和运行库。

这是根据 Makefile、示例配置与当前启动参数确认的缺口；本轮没有重新创建干净环境或为外部用户提供试用账户。**应给一个主入口，清楚区分“留存结果审查”“实时只读调查”“授权业务执行”。** 对每个模式说明数据来源、所需权限和可用操作；保留旧功能作为明确的历史/实验入口。不要复制私人 `.env` 或运行库进 Git 来让启动变简单。

官方要求作品可安装并按描述运行，提供可用的测试访问；不是只有视频即可。公开托管和 AgentCore 是可选加分项，测试可用性本身仍需解决。[官方规则](https://agentsforhumans.devpost.com/rules)

### R06：首页要让运营人员先看到问题与下一步

实际页面的源系统图和引用有用，但当前完成态仍突出 `QUALITY_EVIDENCE_REQUIRED · resolved` 和 `Recorded completion awaiting confirmation`。第一次进入的人不容易立即区分历史异常、业务已完成与留存记录待确认。工具名称也比业务下一步更突出。

建议保留当前企业界面，仅调整信息顺序：**发生什么 → 哪些客户受影响 → 现在缺什么证据/能做什么 → 已经核验了什么**。对完成案例，先给 A25/B15 的发运结果和历史时间，记录确认作为次要操作；对进行中案例，展示当前真正的阻塞。Source 图与工具 trace 可展开验证，不承担解释业务的全部任务。

这不是要求“做成 Duolingo”，也不是再换框架。当前技术栈已经能支持这个改动。

### R07：Agent 必要性仍需一次公平证明

当前合同计划由代码计算，模型选择提供的计划或延后，业务批准与执行属于人和代码。这个边界是优点，但也让评委有理由追问：模型是否只是在复述一个已经算好的答案？

用同一场景比较三者：原生 ERPNext 操作、固定规则+表单流程、当前 Strands 调查。测试问题必须有需要整合的冲突或缺失证据，例如“到齐四箱为何还不能兑现客户剩余需求”“样本失败能否证明全部坏了”“哪条合同允许最后不足最小发运量的尾批”。记录模型读取哪些证据、排除哪个解释、提出哪个必要问题，以及人需要多少次重新录入。

不要为了证明 Agent 而删掉确定性计算；也不要把模型调用次数当收益。对没有歧义的动作，规则自动处理本来就更合适。研究得到的主张应是“减少异常调查和跨系统操作负担”，不是“让所有步骤都由 LLM 决定”。

### R08：真实物理输入与运营效率尚未验证

PO20 的照片是手工附件；数量、质检和交付是明确合成的业务输入。此前独立视觉路径的成功不等于 PO20 已验证从图片自动提取。是否加入扫描，取决于能否用真实清晰的标签减少录入，并在相同订单链上确认再使用；单纯上传一张箱子图片没有完成这一点。

19 个事件和对应人工批准记录是控制证据，不能自动宣传为“只需一次输入”或节省多少人时。应先测物理采集、判断、录入、批准、等待分别花多少精力，再把已有授权范围内的重复软件步骤合并。质检测量和重要处置仍需合适的人提供证据与决定。

## 5. 建议执行顺序

以下是后续更新的具体边界和工作量估计，**不是本轮已实现内容，也不是保证工时**。有效工作时间不含等待权限、用户或外部服务。

| 顺序 | 工作包 | 验收结果 | 估计 / 路由 |
|---|---|---|---|
| 1 | R01 诊断现有身份/模型配置；R04 提供方错误边界 | 原 Ask 成功；失败时正确 UNAVAILABLE，无原始 ARN | 1–3 小时；环境由主审，代码 Terra Max |
| 2 | R02 来源模式贯穿；R03 确认历史事件时返回最新全案状态 | fresh/retained 不混；39→确认旧20→仍39；无新外部效果 | 2–4 小时；Terra Max + 独立审查 |
| 3 | R05 一个可复现主入口；R06 业务摘要与完成态说明 | 另一人按说明进入当前案例，辨认日期/权限/下一步 | 2–4 小时；清晰文案由主审，窄界面改动 Luna Max，配置耦合用 Terra |
| 4 | R07 三回合与一个反例；一个原生流程对照 | 量化少了哪些人工操作，同时保留失败与等待 | 2–4 小时；主审设计，按边界实现测试 |
| 5 | 有余量才做 R08 单次标签/清单提取与确认 | 同一订单中原始图片→确认字段→实际后续使用 | 3–6 小时且依赖合适真实输入；不扩开放式视觉识别 |

**建议在 9 月 13 日先完成 1–3，再决定是否做 4 的最小比较；第 5 项默认推迟。** 这些不是相互独立的整天大项目，不应把每项时间简单当承诺总和。若权限无法及时恢复，应保持真实阻塞状态并继续完成来源语义、恢复和主入口；没有通过的 Agent 不能被替换成静态答案。

商业验证可并行做 3–5 次短访谈，但本轮没有代表用户联系任何人。先问近期具体异常、当前处理人、原生 ERP 如何解决、跨系统重复工作和接入成本，再决定是否值得试点。不要立即扩客户账户、多 ERP、承运商平台、自动财务、AgentCore 迁移或多个 Agent 编队。

## 6. 后续修复的验收与发布约定

每个工作包保留原失败输入 → Terra/Luna 按范围修改 → 主审看实际 diff → 相关回归 → 一次独立复核 → 真实界面/模型或外部读取（按该包需要）→ 一次清晰 commit + push 并核对远端。权限、数量、来源时间和真实效果不能因赶截止而降低标准；不扩大成生产平台重建。
