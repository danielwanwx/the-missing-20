# The Missing 20：旧设计启发、竞争边界与场景扩展

日期：2026-09-12。范围：重新阅读 Claude 的场景设计和现存原型代码，对照 Microsoft/Oracle 官方能力，提出产品定位和最小验证方案。**本轮只有研究与设计判断，没有修复产品、运行新模型比较、访问竞品付费租户或执行业务写入。**

## 判断

**已经有人做，而且 Oracle 与我们的广义叙事高度重叠。不能再把“主动监控→定位异常→分析客户影响→人批准→执行”作为无人覆盖的创新。**

仍值得继续的切口是：为使用 ERPNext 的零部件分销团队，把现场数量/身份/质量证据与系统记录、客户合同拼合，判断哪些部分必须停止、哪些部分可以继续，并核验执行结果。它是有待验证的产品切口，不是已经建立的护城河。已有深度部署 Oracle/Dynamics 并能原生覆盖该任务的客户，优先使用原生能力可能更合理。

比赛的机会来自对具体问题的理解、真实工作完成度和可检查的 Agent 判断，而不是证明世界上没有类似产品。[官方评分规则](https://agentsforhumans.devpost.com/rules)要求创造性、非显而易见的 Strands 应用及领域理解，也同时评价技术、设计、影响和展示；并未把“没有大厂竞品”作为标准。这是对规则的解读，不是获奖预测。

## 1. 找到了哪些 Claude 设计，值得吸收什么

按父目录 HANDOFF 的索引，实际读取了本机 Claude 项目记忆中的 `demo-winning-requirements-spec.md`、`demo-direction-wire-real-agent.md`、`real-vertical-slice-artifacts.md`，并检查父目录 `logisticpilot-po20-ui-prototype/src/App.jsx`。这些是旧设计/历史运行记录，不作为当前能力证明；私人记忆和运行标识没有复制入库。

同时对照仓库的 [异常调查设计](../superpowers/specs/2026-09-03-ambiguous-receipt-quality-investigation-design.md)、[业务场景矩阵](2026-09-06-real-enterprise-exception-case-matrix.md)、[分销流程设计](2026-09-10-distributor-native-workflow-design.md)及 [PO20 历史实际运行](../submission/video-v1/REHEARSAL-V2.md)。较早 100-unit 场景、PO22 的 6 Box 场景与 PO20 的 40 Nos 场景必须分开。

| 旧设计想法 | 取舍与理由 |
|---|---|
| 异常限制在最小影响范围，正常部分先继续 | **保留为主价值。** 从“修一个系统错误”提升为“在有依据的情况下保护可继续履约的部分”。不是所有企业原来都整链停工，不能虚构这样的对照。 |
| 链路某处变红，上下游数字同时解释差异 | **保留交互意图。** 展示业务阶段、批次、客户和证据因果；数据必须来自相同案例，而非前端动画驱动。 |
| 经理点异常后直接问为什么、还能发多少 | **保留。** 解释不能只复述状态，需指出支持/反驳某个处理的记录与下一条必要证据。 |
| 一排人工核对员变成 Agent + 一个人 | **改成待测假设。** 可合并重复软件录入；不能声称已替代岗位，也不能隐藏质检、实物采集、批准和异常处理的人力。 |
| 90 天供应商缺陷率预测与主动告警 | **暂缓。** 现存原型是固定历史、固定阈值和预设文案，没有真实纵向预测验证。批次抽样失败比例也不能直接等于全部产品缺陷率。 |
| QR 精确追到每个问题零件 | **只保留身份/证据导航。** 原型内层零件是标注合成的数据，外箱照片不能证明内件质量或数量。 |

额外发现：现存原型的浮动 `AgentPanel` 是预设回答；`Investigation` 确有真实 API 调用，但失败后回退到脚本文案。收货弹窗和批准主要推进本地 React 状态，供应商趋势来自常量。**这是源码检查结论，本轮未运行原型确认每个显示状态。不能直接把该原型当成主线真实执行界面。** 应吸收它的问题导向布局，将改动留在已接通 `/operations` 的主流程上。

## 2. 大厂已经做到哪里

完整逐项依据与启用边界见 [Microsoft / Oracle 能力证据](2026-09-12-ms-oracle-capability-evidence.md)。以下是影响定位的关键事实。

| 产品 | 官方已有描述 | 对我们意味着什么 |
|---|---|---|
| Dynamics 365 Procurement Agent | 当前概览明确标为 production-ready preview；供应商来信变更、PO 更新和影响分析结合 | “读邮件+追供应商+告诉客户影响”不是新类别。[官方概览](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/procurement-agent-overview) |
| Oracle 26B Warehouse Operations Workspace | 入库短供/延迟、出库风险、库存替代与重分配、跨库供需和可执行建议；受角色、组织与配置限制 | 与“异常限制范围并继续履约”有直接重叠；不能说 Oracle 只提供报表或不执行。[26B 文档](https://docs.oracle.com/en/cloud/saas/readiness/scm/26b/inv26b/26B-inventory-wn-f43846.htm) |
| Oracle Order Exception Assistant | 26A 增强文档描述用户点击 Show Exceptions 后尝试处理 shipping/receiving 未处理响应，并返回任务请求标识；不保证已恢复 | “未处理响应→用户触发重处理尝试→任务标识”也不是独家，尽管不等同于本项目所有业务键/批次分支。[26A 文档](https://docs.oracle.com/en/cloud/saas/readiness/scm/26a/order26a/26A-order-mgmt-wn-f42918.htm) |
| ERPNext 原生流程 | 收货、接受/拒收数量和仓库、质检及库存预留已有支持 | 最重要的基线是目标客户现有配置，不是手工 Excel 的人为弱版本。[收货文档](https://docs.frappe.io/erpnext/purchase-receipt) |

Oracle 的版本化启用文档比新闻稿更能证明功能具体性，但仍不证明所有租户默认启用、许可相同或我们的同一案例已在竞品跑过。Microsoft/Oracle 有扩展平台；“能连第三方”“有权限”“有审计”“human-in-the-loop”“模型加确定性执行”均不能单独成为独家主张。也没有证据证明我们部署更快、价格更低、推理更准。

**最强竞争反驳：** ERPNext 原生配置和少量工作流脚本可能已经足够，额外 LLM 增加成本、等待与不确定性。我们的下一次验证必须认真允许这个结论成立。

## 3. 应该把解决的场景讲成什么

推荐一句话：

> The Missing 20 helps parts distributors investigate receiving exceptions, contain the affected stock, and keep evidence-supported customer fulfillment moving—with approved actions verified in their ERP.

中文：**零部件到货出了差异，帮助运营人员查清原因、隔离受影响库存，让符合证据和合同条件的订单继续履约，并核验系统实际执行结果。**

主场景沿用 PO20，避免将三套历史场景拼成一条不存在的全能演示：

| 阶段 | 已有历史同单记录所支持的事实 | 人真正需要判断的问题 |
|---|---|---|
| 需求 | A 要 25，B 要 15；共 40 件 | 谁先获得可用库存，依据哪些已配置合同？ |
| 第一批 | 20 件获得质检放行，A20 已发运 | 为什么可以先履约这部分，而不是等待整个 PO 完结？ |
| 第二批 | 两箱内件共 18，另缺 2；样本失败后 18 待处置 | 四个原始箱子都到了，为什么还不能发剩余 20 件？ |
| 纠正 | 全批复检放行 18，方案为 A5/B13；补货 2 后只追加 B2 | A5 为什么可小于常规最小发运量？如何避免重新占用已准备的库存？ |
| 结果 | 系统累计发运 A25/B15 | 哪些原生记录证明发运？哪些记录不能证明物理签收和收入？ |

数量、测量和交付事件是披露的合成业务输入；ERP 写入/读回是历史真实 demo-tenant 效果。本轮 9 月 12 日审查已确认当前 ERP 总量，但当前新 Agent 调用失败，见 [运行审查](../audits/2026-09-12-return-to-project-review.md)。这里没有声称当前再次完成了上述阶段。

Claude 的“最小影响范围”在这里可以具体化为 **A20 已经先走，第二批到货的待处置问题不撤销已有的合规发运**。该批后续分给 A5/B13，不是只影响客户 B。不把 20/40 的场景数量称作生产节省率，不声称全链原本必停，不把缺两件推断成供应商过错或丢失。

## 4. 如何让评委看到竞争力，而不是听到定位口号

| 主张 | 最小可观察证明 | 哪种结果会削弱主张 |
|---|---|---|
| Agent 能处理证据冲突 | 同一表面“缺 20”，分别提供未入账、已入账但响应丢失、质量未放行的证据，给出不同方案/停止理由 | 只是根据预先给定的结论卡复述；换事实仍答同一模板 |
| 减少运营人员拼接信息 | 与原生 ERP + 已有规则流程做同任务对照，计入全部录入、系统切换、等待、重试和批准 | 只是把原来的点击改为更多聊天，没有减少实际工作 |
| 保护可继续履约的部分 | PO20 的可用/held/已发运/客户剩余量分开；修改合同后能解释为什么新方案改变 | 固定优先级被误称为动态优化；质量未放行仍分配 |
| 真实闭环且范围受控 | 展示批准对象、实际原生单据和新回读；重复请求无重复效果；拒绝时状态不变 | 只看成功工具返回，或用 UI 本地变色当执行 |
| 不是只支持一个编号 | 第二个案例使用新 ID/UOM/分批规则和证据，沿用同一调查与核验流程；报告新增了哪些适配 | 实际只是改标题和数字，或为第二例塞进独立硬编码路径 |

建议的“缺 20”三分支来自早期 100-unit 调查设计，是一个**单独的对照实验建议**，不能当作当前 PO20 已通过。先选两个最有区别的分支，冻结输入与判定标准，再做真实调用；没有时间就不把旧 fixture 写成新验收。不要为比赛临时实现完整 ERP/消息队列故障模拟平台。

Agent 的作用是选择要查的证据、比较解释、询问必要缺口和说明方案依据；数量守恒、合同约束、授权和写入核验继续由代码及原生系统负责。若固定规则对选定任务同样好且更简单，应承认其优点，重新选择真正需要调查的部分，而不是故意增加 LLM 决策。

## 5. 能否扩展到不同场景

**可以提出复用路径，但目前不能称作已验证的通用平台。** 场景扩展、ERP 适配、吞吐扩展和客户交付是四件不同的事。

| 扩展方向 | 可复用部分 | 必须新增/验证的部分 | 建议 |
|---|---|---|---|
| 同一 ERP 的其他零件、供应商、分批到货 | 证据引用、数量/UOM边界、批准、原生执行与回读 | 新主数据、批次和合同策略；不能复用旧案例事实 | **最近的扩展验证** |
| 已记账但回执丢失、重复交接 | 当前业务记录查证与无操作结论、动作身份 | 各集成的结果未知语义和真实目标查询 | **适合做第二类调查分支** |
| 供应商退货/返工 | 质量证据、批次身份、审批和事件记录 | 原生退货/返工单据、返工责任和重新验收 | **赛后相邻方向**，不是换提示词即可 |
| 供应商发票匹配异常 | 来源/版本、调查与批准结构；历史独立案例可供参考 | 发票来源、匹配规则、独立财务权限；不能从收货自动推导付款可放行 | 赛后单独纵向验证；当前 PO20 没有已链接发票 |
| 另一个 ERP，如 Oracle/Dynamics | 业务问题分类与部分证据契约 | API、原生单据语义、权限、版本、限流、回读和幂等机制 | 尚未实现；不称 vendor-agnostic |
| 多租户/高并发/生产自动化 | 少量现有事件与日志结构可供起点参考 | 租户隔离、队列、权限生命周期、故障/负载验证、运维成本 | 本轮未测试；不是已有规模能力 |

合理的共享结构是：**发现事实不一致 → 读取有范围与时间的证据 → 区分解释和影响 → 形成受约束方案 → 人作必要决定 → 原生执行 → 回读 → 继续等待新的证据。** 各场景需要各自的事实定义、动作和通过标准。它是设计上的复用判断，当前代码的耦合程度与新增第二场景成本仍需实际测量。

无需在截止前抽象“通用场景引擎”。先跑第二个语义不同的案例，记录需要改什么，再从实际共同部分抽象；如果每新增一例都改核心状态机，就是扩展成本证据，应如实记录。

## 6. 对下一轮更新顺序的影响

1. 先完成现有审查中的可用性与证据时间修复。没有真实 Agent 成功，不应继续强化自动化宣传。
2. 主流程增加清楚的“可继续 / 必须等待 / 原因 / 受影响客户”摘要，借鉴旧原型布局，不移植其静态执行和失败回退。
3. 在 PO20 历史事实与新真实验收之间保持边界；用一个新的只读对照分支检验不同解释，不重置已完成订单。
4. 保留两个竞争基线：原生 ERPNext + 配置，以及固定规则 + 表单。大厂按官方能力比较，没有付费租户实测就不宣布击败它们。
5. 赛后找 ERPNext 实施伙伴和分销运营核实近期异常、现有解决方式与集成成本。若同任务原生方案已足够清晰，就缩小 Agent 职责或换具体问题，而不是继续加连接器。

本轮不修改 Devpost、视频或产品代码。研究结论不取消原有工程修复优先级，也不证明获奖概率、用户付费意愿或岗位替代规模。
