# The Missing 20 产品目标与竞赛评审

## 判断与决策

**继续验证零部件分销的异常调查与履约保护，但当前证据不足以把作品列为获奖强候选。下一轮最有价值的提升，是证明 Agent 在一个真实任务中比规则流程多完成了必要工作，并用独立评估支持这个结论。增加 Agent 数量不是目标。**

工程基础包括历史真实 ERP 执行、同订单客户分配、Strands 问答、来源引用与批准记录。薄弱处包括最新已知的模型访问失败、留存资料新鲜度错误、缺少对照的 Agent 增量价值，以及供应商趋势所需的数据基础尚不完整。测试数量与历史演示不能分别替代模型行为评估和当前可用性。[^runtime]

这份评审基于截至 2026-09-12 的代码、既有实际运行证据、官方规则和公开一手讨论。它不代表官方评委，没有新竞品租户实测、生产试点或获奖概率估计。评审围绕产品与技术；未重新审看视频，因此不提供五项完整总分。

## 1. 痛点应如何定义

最清楚的痛点是：**系统看起来有货，但运营人员无法立即确定它是否真的可以用于某个客户的发运；销售、仓库、质检和采购各持一部分信息，必须有人把证据拼起来，决定继续什么、等待什么、找谁补证。**

公开用户讨论直接描述了销售已承诺交期，而物料其实处于预留、加工或未准备发运状态。它把系统库存与客户承诺的联系说得很清楚。同一讨论提出了净可用量、质检状态、预留与权限规则等解决办法，因此也构成对“必须使用 AI”的反证。[^promise]

另一位自述经营零配件业务的匿名用户，明确需要处理格式不一的邮件、RFQ、消息和照片，再查库存及客户条款，由人复核准备好的报价和订单。作者认为原有流程错误很少，主要问题是工作量增长；该案例支持减少录入与信息整合，不支持宣称人工流程普遍不可靠，也不直接验证收货产品。[^parts]

ERPNext 的拒检入仓、返工和部分接受讨论，以及 DigiKey 重复错件的用户案例，支持实物、身份、质量与系统记录之间存在需要解释的差异。不过，早期版本问题已有后续配置/实现，不能作为当前竞品缺陷宣传；公开支持帖也不能提供市场规模或产品付费意愿。逐条证据与反证见 [需求证据台账](2026-09-12-demand-falsification-evidence.md)。[^quality][^wrongpart]

### 目标用户和工作边界

| 项目 | 明确要求 |
|---|---|
| 第一位用户 | 使用 ERPNext、负责收货异常和客户履约协调的零部件分销运营人员 |
| 其他责任人 | 收货员提供实物观察；质量负责人提供检验与处置；销售/运营决定客户优先级；系统保留这些权限差异 |
| 触发 | 到货/质检新证据、源记录冲突、临近承诺日期仍缺可用库存，或有足够可比历史时出现重复异常信号 |
| 用户要完成的任务 | 查清当前能做什么，获得可核查的依据，补齐必要证据或授权明确动作，看到执行结果 |
| 核心产物 | 一个同案例的决策记录：事实、冲突、受影响客户、可继续数量、待补证据、建议、批准与回读 |
| 系统不代替的工作 | 实物测量、质量放行权、客户承诺权和金融权限；不能用模型文字填补这些事实或授权 |
| 赛前范围 | 一个 ERP、一条真实同订单业务链、一个具有不同正确处置的对照分支；不扩展为通用 WMS |

推荐产品表述：**持续关注收货与履约风险，查清异常背后的证据差异，让符合条件的客户订单继续推进，并核验处理结果。** ERPNext 是第一个支持的系统，零件分销是第一个验证场景；产品当前没有跨 ERP 通用性证明。

### 为什么这个任务可能需要 Agent

明确的数量计算、库存预留与阈值比较通常不需要 LLM。Agent 的候选价值在于：面对未预先归类的描述与来源冲突，选择下一项要查的事实；区分几种解释；指出哪条证据会改变决定；把业务规则与该案例联系起来；向人询问一个必要且可回答的问题。

如果每个案例都已经由代码算出原因和唯一方案，模型只负责选同一个 plan ID 或复述结果，那么“自主调查”的主张很弱。应通过对照揭示这一点，不应为营造 Agent 感而故意削弱原生规则。

## 2. 竞争与原创性的真实边界

Oracle 的仓库工作台已公开入库异常、库存与客户需求对齐、纠正建议及行动；其 Agent Studio 能调用第三方 API 并要求人工批准。Microsoft 的采购 Agent 已结合供应商变化和下游影响分析。主动、跨系统、human-in-the-loop 均不是独家。具体版本和边界见 [官方能力对照](2026-09-12-ms-oracle-capability-evidence.md)。[^oracle][^oracletools][^microsoft]

ERPNext 原生接收/拒收、质检和预留是必须认真比较的基线。如果正确配置加少量脚本已经解决目标任务，就不应增加一个难维护的智能层。[^erp]

可以争取的区别是**某一类用户中的任务完成质量**：碎片化证据是否少查了、错误恢复是否避免了、可继续的客户份额是否明确了、下一位操作人员是否不用重新调查。它需要记录和对照，不能由领域名词、架构图或连接器数量成立。

原创性有三个层次：库存/质量管理这个类别已经成熟；将证据冲突调查与最小范围处置结合，具有领域应用价值；是否形成难以复制的商业优势，仍需要客户工作流、长期数据质量、集成维护和实际使用的证据。比赛可以奖励第二层，但不能把它冒充第三层。

## 3. 最小产品需求与成功目标

以下是建议冻结的需求和验收目标，均不是本轮已经新增的能力或完成结果。

| 优先级 / 需求 | 用户可观察行为 | 验收证据 |
|---|---|---|
| P0 当前可运行 | 同一页面发起真实调查，模型不可用时准确说明状态、保留输入 | 最新真实请求成功与一次受控失败；实际模型和来源模式可查 |
| P0 来源正确 | 明确区分现场观察、ERP 记账、质量处置、历史记录和建议 | 同样问题在 current / retained / unavailable 下正确改变结论；引用匹配案例/版本 |
| P0 业务下一步 | 回答谁能发多少、谁必须等待、缺哪条证据 | 数量/UOM/批次/合同一致；可用库存与 held 库存不混；不把样本失败当作全批实测失败 |
| P0 必要调查 | 在两个合理解释之间读取决定性证据或请求补证 | 可见工具参数与返回引用、解释改变原因；未知不是一律成功拒绝 |
| P0 执行与闭环 | 人批准具体计划后，原生系统完成；未批准不执行 | 相同批准范围和来源版本；原生结果及回读；重复请求无重复业务效果 |
| P1 当前风险监测 | 来源更新或定时检查触发“交期临近但未放行/可用量不足” | 实际触发时间、来源日期、去重记录；能从告警进入同案例调查；不是仅点击才计算 |
| P1 易理解 | 一眼区分可继续、必须等待及原因；按需展开证据 | 新操作者说清问题和下一步；不必先解释技术架构 |
| P1 可测改善 | 相同任务比较规则流程、单 Agent 和必要的多 Agent 候选 | 正确完成、错误升级、补证质量、人工操作、等待、重试与成本全部保留 |
| P2 趋势监测 | 有足够可比业务事件时，解释重复异常及其关联订单 | 真实窗口、分子/分母、批次范围、缺失和基准来源；不足时明确不支持趋势结论 |

两个产品结果目标应分开：第一，正确完成可以完成的任务，并正确停下必须停的任务；第二，在没有增加错误和维护负担的前提下，减少人的查找与重复录入。获奖、岗位替代、节省百分比与收入增长不能作为未测结果填写。

用户研究可先做三个同任务走查，报告每次实际操作与全部等待；样本太小不能推断生产效率。没有真实运营人员时，内部走查只证明可用性，不能称为客户验证。

## 4. 用哪个业务场景体现价值

主线沿用 PO20 的历史真实 ERP 链路，不重新拼接旧 100-unit 场景与 PO22 箱数场景。

1. 客户 A/B 需要 25/15 件。第一批 20 获得质量放行后先发 A20。
2. 原始四箱都已到，但总内件只有 38；第二批 18 因样本失败等待处置，另缺 2。
3. Agent 应解释：四箱不证明 40 件；样本失败可支持隔离，不证明 18 件都实测不良；已发运的 A20 与剩余需求分开。
4. 新的全批复检证据支持放行后，现有合同方案是 A5/B13；补货后追加 B2。必须解释 A5 尾批例外、已有承诺和实际执行状态。

这些阶段有历史演练记录，实物/质检/交付输入明确为合成，ERP 效果为 demo tenant 真写入。最新运行问题不能被历史演练成功覆盖。[^runtime][^rehearsal]

最有信息量的新增调查是**改变一个关键事实而得到不同处理**：例如质量放行材料属于别的批次，或当前数量来源无法读取。它应在单独的受控案例中验证，不能修改已完成订单来制造未解决的状态。

“已经入账但回执丢失”仍是有力的另一个问题家族，但属于旧调查路径；只有在当前入口真正接通并验收后，才能用于证明同一产品的第二类场景。

## 5. Strands 应体现在哪里

官方规则要求有实质的 Strands 实现与端到端工作；没有规定必须使用多 Agent 或某个 Evals 类。技术是首个平分决胜项，AgentCore 和可用演示可加强技术评分，但不会抵消主任务不工作。[^rules]

现有系统包含三种不同层次，不能互相借名：

- 旧 `agents/harness.py` 有三个调查角色并发，再综合与评估；编排由应用代码持有。这证明存在多 Agent 实现，不证明当前 PO20 主流程运行了它。
- 另有 `agents/role_delegation.py` 的应用自管 Agents-as-Tools 角色咨询，接在更广的调查路径上；同样不能当作当前 distributor 对话的执行轨迹。
- 当前 distributor 原生对话用 Strands Agent、工具和会话。源码显示来源 payload 已在回合前装入，reader 返回其副本，当前回合消息也包含来源内容。工具调用可证明模型访问了这些 payload，不能逐次称为新外部查询。
- `agents/distributor_allocation.py` 中的模型从代码算好的方案选择 plan ID 或 DEFER，不自由制定数量。这个约束是正确边界，但不能把它包装成自主库存优化。

主应用环境安装 Strands Agents 1.53.0，已有 Graph/Swarm 导入；本轮核对主环境未安装 Strands Evals。另一 AgentCore 环境的版本不代表当前应用版本。官方机制、安装版本与 Evals 差距见 [SDK 证据报告](2026-09-12-strands-multiagent-evals-evidence.md)。当前路径的 Agent 贡献要通过改变证据、查询和任务来验证，而不是把旧框架的角色图放在新案例旁边。[^local]

### 单 Agent 基线

给一个 Strands Agent 有范围的查询工具：案例索引、收货/质量证据、客户合同、相关源状态和可用流程知识。工具只读，返回来源标识、时间和范围；可缓存，但必须标注缓存与新读取的差异。让 Agent 选择需要的资料并解释缺口；数量计算和动作权限保持确定性。

不能为了让工具调用看起来更多，隐藏一个正常产品本来就应展示的字段。对照必须给予相同的信息可达性和相同的必要事实；评估器答案与最终裁决不放进模型输入。

### 多 Agent 候选

建议最多两个专业调查角色，在固定的隔离比较中并行调查，再由案例协调者综合。简单案例也纳入，以观察不需要拆分时的额外成本：

| 角色 | 独立任务 | 返回内容 | 权限边界 |
|---|---|---|---|
| 收货与质量调查者 | 区分到货、内件、UOM、批次与检验范围；找出矛盾和需要补充的物理证据 | 有来源的事实、支持/反驳解释、缺口；不自授放行 | 只读 ERP 收货/批次、质量、实物观察及相关知识 |
| 客户履约调查者 | 读取客户需求、合同、已有分配与承诺，说明可能受影响的订单和约束 | 合同引用、客户影响、可行方案前提；库存未确认时不声称可发 | 只读订单/合同/预留及相关集成、协作记录；必要重叠范围需声明 |
| 案例协调者 | 综合专业角色的已核查观察，识别结论冲突，请求补证或提交约束完整的方案 | 面向人的下一步及证据说明 | 不直接写 ERP；共享案例/源版本边界 |

初次隔离实验选官方 Graph 固定两个分支，避免把“是否调用专业角色”也变成新的实验变量；join 必须检查两方结果齐全、案例与源版本相同，不能把图调度本身当作完整性验证。按需咨询可复用 Agents-as-Tools 的思路，但不在这一次同时比较第三种多 Agent 结构。不要同时引入 Graph、Swarm、A2A 和新持久化框架。业务执行仍使用已授权的受控路径，SDK 的中断或会话机制不等于跨 ERP 原子事务或恰好一次效果。[^strands]

多 Agent 只有在单 Agent 漏掉必要证据、上下文过载或独立专长确有收益时才值得保留。若两个角色都重复读取完整数据、输出相同解释，增加的调用是负担。相同模型与同一证据也可能共享偏差，角色分工本身不能称为独立真值验证。

## 6. Evals 的具体设计

需要区分四件事：产品中的“评估 Agent”是运行时审查者；代码验证器检查可计算约束；测试用例检查实现；Strands Evals 组织针对行为的实验。它们不能相互替代。让一个模型说另一个模型“很好”，不证明真实 ERP 状态正确。

### 评估分层

| 层次 | 检查什么 | 真值与工具 |
|---|---|---|
| 事实和业务效果 | 数量/UOM、批次、合同、来源时间、未授权效果、重复效果 | 独立预期、源记录和确定性断言；必要时真实 ERP 回读 |
| 调查过程 | 是否查了决定性证据、越权读了什么、是否重复无效查询、是否在来源不足时询问正确缺口 | 实际工具参数/结果/actor/时间；按角色权限评估，不要求唯一固定调用顺序 |
| 回答与任务完成 | 是否直接回答用户问题、引用是否支持结论、有没有把观察变因果、应完成的是否完成 | Strands Evals 的适当 evaluator 或自定义 rubric，辅以盲审校准 |
| 产品成本 | 人主动操作时间、总等待、全部尝试、模型/工具消耗、完成率 | 实际日志与同任务走查；不能把被拒绝的任务全部算成功 |

官方 Strands Evals 提供 case/experiment 与多类评价机制；实际可用 API 及版本应按证据报告冻结。LLM trajectory 评分可以帮助审查路径，但不能单独授权库存动作；工具列表与权限必须按 actor 区分。[^evals]

### 最小实验，而不是一张漂亮分数图

建立 12 个受控任务：4 个用于开发，8 个留作冻结后的评估。这里仅定义问题家族，具体输入与答案须由独立评审在实现候选冻结后准备，不能把本报告当成已经隐藏的测试集。

应覆盖正常分批、明确短收、样本失败/全批隔离、错误批次的放行证据、缺 UOM 转换、已入账但回执丢失、来源更新使旧方案过期、来源不可用。只有已接通的业务路径能参加该路径的端到端评估；其他问题家族标为隔离实验，不能凑成当前主流程通过率。

比较三组：原生规则/表单基线、单 Strands Agent、协调者+两个专业角色。规则基线保留其实际需要的人工调查，不能按聊天文风评分，也不能故意缺少它平时有的配置。两种模型候选使用同模型、相同可达证据、相同任务和预先固定的预算；展示实际消耗，不能把更多总 token 的结果说成结构本身的收益。

最小冻结评估为 8 个任务 × 2 个模型候选 × 2 次重复，共 **32 个真实模型工作流运行**；开发调试、子 Agent 调用和评分模型成本另计并全部记录。它是小样本工程比较，不足以宣布生产准确率或统计显著优势。若预算或权限不支持，减少范围并明确未覆盖项，不能用脚本输出替代真实模型成绩。

每次保存案例与数据版本、问题、模型配置、工具轨迹、来源引用、候选输出、所有错误/超时、人工修正、消耗和逐项裁决。重试必须计入开始次数与总成本；同一失败不能无限重跑取最好结果。开放的文案判定先用人工标注样本校准评分器，并打乱候选标签，避免同一模型自评成为唯一依据。

建议冻结的晋级门槛：关键业务错误、未经授权效果和重复效果在受控验收中为零；至少两个不同困难任务，在两次重复中都修正了单 Agent 的同类必要事实/调查缺口，且其他任务不退步；最后检查预先确定的总预算与可接受等待。它是工程选型规则，不是统计显著性标准。若单 Agent 已全部完成，则多 Agent 只能凭可重复的效率改善争取保留，不能因模型更多而晋级。实际模型、每任务总 token/费用/时间上限需在开始前记录，当前未冻结金额或开始付费实验。一次更漂亮的回答不构成晋级理由；两次相同机制失败后先研究原因，不继续叠提示词。

**真实模型对冻结记录的评估 ≠ 当前在线来源验证 ≠ 真实业务写入验收。** 对选定方案还需一次同案例真实网页与外部读回；不为每个评估样本重新创建 ERP 订单。测试材料中的缺陷趋势或实体观察必须标明合成。

## 7. 主动监测与知识库仍然保留

主动性应表现为事件或定时检查触发任务，并在新证据到来后继续，而不是非要在前台增加一个名叫 Monitor 的模型。第一版可以用确定性监测发现“临近承诺但质检未完成/可用量不足”，再把存在歧义的情况交给 Agent 调查。

本地知识库当前是六篇有版本的流程与定义；`operational_history.py` 保存范围化业务观察并计算内部观察基线。知识库解释规则，历史数据描述变化，当前系统证据决定本次可行动条件。这些已存在的部件不能自动等于 PO20 已具备跨供应商长期风险监测。[^history]

不要将多次轮询同一订单视为多个独立供应商批次，也不要将累计库存快照平均数称为缺陷率。趋势需要明确事件粒度、可比物料/供应商、时间窗口、分母、缺失和数据覆盖。第一次应优先重复异常计数与有依据的阈值，不宣称预测下一批失败概率。

较完整的目标链是：**风险信号 → 哪些订单可能受影响 → 需要查哪条事实 → 哪些部分可继续 → 谁需作决定 → 新证据后恢复 → 结果进入后续历史。** 其中每一步都必须标明当前已实现、隔离实验或后续计划。

## 8. 模拟 Devpost 严格评审

下表使用内部 1–5 分尺度：1 为未形成可工作的证据，3 为有实质原型但关键论证有缺口，5 为范围清楚、工作完整且有强验证。它不是官方评委打分，不是获奖概率。最新运行依据沿用 9 月 12 日审查，本轮未再次执行 Bedrock。[^runtime]

| 官方维度 | 当前暂评分 | 会被质疑什么 | 争取更高评价所需的证据 |
|---|---:|---|---|
| Technical Implementation | 2/5 | 有真实 ERP 与 Strands 历史实现，但最新核心问答不可用；旧多 Agent 与当前主链没有相同运行证明 | 修复原失败；当前主链真实成功；冻结行为评估；多 Agent 是否保留由对照决定 |
| Design | 3/5 | 已有完整业务页面和证据，但需要解释旧状态、留存模式和不同入口 | 首屏清楚告诉运营人员现在能做什么；从信号到回读同案例贯通 |
| Potential Impact | 2/5 | 痛点有公开依据，但发生频率、实际省工、采用成本没有项目级证据 | 一个真实任务走查及原生基线，报告全部重试/人工步骤；没有就保持影响为假设 |
| Creativity & Originality | 2/5 | 大厂覆盖相近链路；当前模型的一部分工作是解释预计算结果 | 展示非平凡证据冲突、必要补证、同告警不同处置及可重复的 Agent 增量 |
| Presentation | 未评分 | 本轮未重新审看视频，不能判断视频端到端清晰度 | 后续按官方要求核验问题、受众、价值和真实运行，不借历史包装抬高技术判断 |

四项诊断不合并成官方五项总分。演示访问和运行一致性也是资格/功能要求，不仅是可选的美化。技术与原创性要提高，优先让评委看到一个 Agent 根据证据改变行动的过程，再展示评估如何验证其不是碰巧答对。[^rules]

## 9. 截止前的执行取舍

| 顺序 | 工作包 | 完成定义 | 不应顺带扩展的内容 |
|---|---|---|---|
| 1 | 修复模型访问与来源时间/历史确认缺陷 | 原失败被真实验证修复；错误状态准确 | 更换整套模型/框架、无关生产硬化 |
| 2 | 冻结上述用户任务，建立单 Agent 与规则基线 | 同案例可正确调查、解释和受控完成 | 为显得 agentic 增加无必要工具调用 |
| 3 | 隔离实现最小 Evals 适配与两专业角色候选 | 有逐例配对记录、真实模型调用和明确未覆盖项 | 全套可视化评估平台、多框架迁移 |
| 4 | 按证据选择单/多 Agent，接回主入口 | 对选择理由有结果支持；完成一次真实同路径验收 | 同时保留多个未经验证的“高级模式” |
| 5 | 当前风险触发与业务摘要 | 真触发、真来源、同案例下一步与去重 | 90 天虚构趋势、预测准确率、自动采购/付款 |

Evals 的第一项用途是帮助删掉无收益的复杂度。若没有时间完成候选比较，就提交经过验证的较简单方案并说明边界；不能为了声称使用多 Agent 而把未经比较的角色挂到主流程。

后续核心/耦合实现由 Terra Max 承担，固定接口的小改动由 Luna Max 承担；主审负责实验设计、实际 diff、验收与独立复核。每个完成工作包独立提交并推送。这个要求不授权新增外部业务数据或扩大权限，也不把研究方案当成已实现内容。

## 10. 需要从真实操作者那里回答的问题

1. 最近一次“系统有货但不能发”的具体例子是什么？关键事实分别在哪？哪个事实一开始不知道？
2. 当前 ERP 的预留/质检/可承诺量设置是什么？为何原生流程没有解决？是否只是配置缺失？
3. 为了决定下一步，实际查了几份材料、问了几个人、重新录入多少字段？哪些步骤本来可以自动化？
4. 哪些错误处置最不能接受，谁有权决定质量释放和客户优先级？
5. 愿意用脱敏案例走查或允许受限试点吗？若不会使用，具体原因是频率、权限、成本、信任还是现有功能已够用？

这些问题尚未通过真实访谈回答。公开资料已经足以否定“市场空白”的主张，并支持一个有限的任务实验；继续无限增加网页来源不会替代用户任务和对照结果。
