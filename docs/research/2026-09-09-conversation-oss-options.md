# OSS options for complete, grounded receiving conversations

Verified: 2026-09-09. Scope: public primary sources and a narrow read of the current Python Strands/Nova Pro advisory path. Research only; no dependency installed, upstream code executed, business record changed, or framework migration performed.

Recommendation: retain Strands and the existing application boundary. Reuse its structured output, hooks and bounded repair; add question-specific completeness checks and a small recorded multi-turn evaluation set. Strands Evals is the best first optional evaluation dependency. Promptfoo is an alternative external regression runner; DSPy/GEPA is a later offline optimization experiment; LangGraph offers useful state concepts but does not justify replacing this runtime.

## Existing capability and actual gaps

This is the pre-change inspection baseline for this research, not a claim that the
same limits remain after the accompanying R3 implementation. See the linked
[implementation and live-test audit](../audits/2026-09-09-r3-receiving-jira-conversation-review.md)
for changes, failures and verified outcomes.

Local evidence: `src/the_missing_20/agents/receiving_advisory.py`, `src/the_missing_20/agents/live_advisory.py`, and the transcript construction in `src/the_missing_20/adapters/live_advisory_gateway.py`.

- The project already declares `strands-agents>=1.53.0,<2`, uses Pydantic `LiveAdvisoryResult`, requires exact admitted/read evidence IDs, has `_EvidenceCompletionHook`, records runtime telemetry, and performs targeted repair within a wall-time budget. Adding another agent loop would duplicate existing mechanisms.
- Both the receiving prompt and `reason` field description impose fewer than 80 words; `reason` also has an 800-character schema limit. This is a plausible pressure toward omissions in compound questions, not proof that length alone caused every failure. The receiving packet sets `expected_reason_quantities=()`. The receiving-specific checker inspected here primarily enforces notification-copy authority wording; requested receipt identifiers, baseline sample counts and all question parts are largely prompt instructions rather than enforceable completeness requirements.
- The prompt already distinguishes repeated cumulative snapshots from new receipts, requires actual prior sample count/minimum, and forbids copying old assistant claims as evidence. Repeating these instructions alone would not introduce an independent check.
- Conversation context already exists: the gateway reconstructs up to three recent turns, truncating each question to 300 and answer to 650 characters, and labels prior dialogue as context rather than current evidence. `_invoke` creates a new Strands Agent for a turn. A session library therefore addresses richer native history only if needed; it is not a prerequisite for basic follow-ups and must not turn stale tool results into current stock evidence. This narrow inspection does not establish full persistence coverage across every restart/client path.

## What to reuse and implement next

1. **Make completeness inspectable.** Derive a compact list of obligations from the newest question and source packet: requested yes/no decision, exact requested receipt/ledger IDs, requested quantities with source UOM, and requested baseline count/minimum. Keep evidence identity/arithmetic checks in application code; let the model explain them. A valid output schema alone does not prove that every question part was answered. Strands already supports focused Pydantic output schemas and validation retries. [Structured output documentation](https://strandsagents.com/docs/user-guide/concepts/agents/structured-output/).
2. **Remove conflicting brevity pressure.** Permit enough space for a compound answer and align prompt, schema and UI limits. Retain bounded output; prioritize required facts over optional suggestions. Reuse the existing repair path with explicit missing-obligation feedback, the same admitted evidence and existing budgets. Do not add an unrestricted reflection loop.
3. **Keep history grounded.** Retain prior human intent/references and validated answer context; refresh current source facts each turn. Distinguish observation IDs from receipt events and use existing computed first/latest/net-change facts. If native session persistence later replaces transcript construction, use a case-scoped stable identifier and test stale evidence, concurrency and restart behavior. Current Strands docs recommend `SnapshotSessionManager` for new single-agent sessions and document compatibility managers, but compatibility with the installed version must be checked first. [Session management](https://strandsagents.com/docs/user-guide/concepts/agents/session-management/). LangGraph similarly separates thread checkpoints from application-defined cross-thread stores; that is a useful design distinction without importing its runtime. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence).
4. **Treat suggestions as answer extensions.** Reuse the existing `follow_up_questions` field. Generate zero to three distinct, source-answerable, read-only suggestions after satisfying the current request; suppress repeated topics and requests the user already declined. Suggestions should resolve an actual remaining uncertainty, such as which ledger entry supports an identified receipt, rather than repeat a generic next step. This is a project-specific design recommendation, not a capability automatically supplied by any repository. Preserve separate approval handling: an interrupt/resume mechanism does not itself establish authorization, and replay can re-run code before an interrupt. [LangGraph interrupt semantics](https://docs.langchain.com/oss/python/langgraph/interrupts).
5. **Evaluate before adding an optimizer.** Use current recorded failures as fixed multi-turn cases, then attach Strands Evals when reusable reports/trajectory judging add value. Its output/trajectory/interaction features support this reuse. [Evals README](https://github.com/strands-agents/evals). Promptfoo can express multi-turn fixtures and custom assertions as an alternative. [Chat evaluations](https://www.promptfoo.dev/docs/configuration/chat/), [assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/). GEPA is appropriate only after metrics and held-out cases exist: it proposes instruction changes from scored feedback, so weak metrics merely optimize the wrong target. [Official GEPA explanation](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/diving-deeper/gepa-in-depth.md).

## Proposed bounded verification loop

Goal: answer every requested part with current source support while retaining conversational continuity and read-only behavior. Inputs: frozen source packets, newest questions, prior turns and source-derived expected facts. Execute: run the existing Strands path; check independently; permit existing bounded repair; record verdicts, missing obligations, citations, calls, latency and usage. Failure: repair missing supported facts; explicitly state unavailable facts; never invent facts to make a test pass. Stop when the fixed cases pass within budgets, or report the exact remaining failures. This research step grants no authority for paid live-model evaluation or business writes.

Minimum cases:

- A compound request asks whether to retry a submitted receipt, whether an outstanding order means lost stock, and which exact ERP records verify it: all three parts must appear with supported IDs.
- A follow-up asks why a baseline is insufficient: when the source says two comparable prior samples and a minimum of three, state both; never hardcode those counts for other packets.
- Repeated snapshots of the same cumulative receipt balance must not be summed into new deliveries; trend prose must match first/latest/net change.
- A later source contradicts an earlier assistant answer: use and cite the refreshed source, resolve the user's reference, and correct the earlier claim.
- Notification copies cannot prove stock; an unresolved arrival cannot be cleared by a flat chart; refusal/read-only intent must persist into suggestions.
- Candidate suggestions must be distinct, relevant, supported by available reads and absent when none adds value. Mandatory fact/safety failures cannot be offset by a high style score.

Start with deterministic assertions for exact IDs, source counts, arithmetic and forbidden write claims; use a separate rubric for coverage, reference resolution and suggestion usefulness. Compare before/after on the same cases and hold out paraphrases. No quality improvement is claimed until the implementation passes these checks.
